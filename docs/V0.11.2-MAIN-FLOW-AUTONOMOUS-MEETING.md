# Eason One V0.11.2 — Main Flow and Autonomous Meeting Recovery

This release is a bounded recovery of the two product-critical paths:

1. Founder → CEO → Real Mission → Engineer → WSL2 Codex → Windows host validation → Result.
2. Founder → CEO → evidence-bearing employees → automatically governed Meeting → Minutes/Decision → Mission completion.

## Confirmed failures repaired

- Direct `Query.get()` and indirect `Query.get_or_404()` SQLAlchemy 2.x warnings are removed from application routes.
- Codex output is validated by the Windows project virtual environment after WSL2 execution.
- A host test-environment problem is reported as `VALIDATION_ENVIRONMENT_FAILURE`, not a false Codex boundary violation.
- The protected-data boundary no longer snapshots the live SQLite database that Eason One itself is writing during execution.
- Terminal Mission rendering preserves the latest employee Run and live command/event history instead of resetting to zero.
- Real Missions never expose the System Validation archive control.
- Existing Eason One evidence is retrieved across persisted CEO dialogue, Projects, approved Company Brain knowledge, and Research records.
- Earlier Task results are passed forward to later Tasks and the governed Meeting.
- Low-cost and no-premium authority constraints are enforced again at runtime; they cannot silently fall back to Claude Sonnet or Mock.
- Missing evidence blocks before a paid Provider call.
- A one-round specialist Meeting excludes the CEO chair from paid speaking turns unless the CEO is explicitly approved as a participant.
- Meeting token authority is sized for the approved participant count, so a valid two-person Meeting is not blocked by an impossible envelope.

## Existing Mission recovery

- Mission #6 is completed during migration after the installer verifies the remaining SQLAlchemy changes from Windows.
- Mission #8 is preserved and made ready for one bounded resume under its existing NT$20 authority. The original paid failed Run remains auditable and is not replayed automatically.

## Installation verification

The installer runs 57 focused regression tests with `LegacyAPIWarning` treated as an error, then migrates the real database and verifies a copied post-migration snapshot. Installation makes no Provider call and runs no real Codex task.
