# Eason One v0.20 Engineering Constitution

This document is a release-blocking engineering constraint for the Eason One Company Core. It is not product copy and is not optional guidance.

## 1. Governing authority

1. The **Founder Project Contract** is the highest durable authority for a Project.
2. A Project Contract freezes objective, Founder success criteria, constraints, the base budget limit, and deadline. Internal agents may not rewrite it. Any later Founder-approved budget expansion must be an append-only Contract Amendment; the base Contract and its hash remain unchanged.
3. The authoritative business spine is **Project → Work → Execution → Artifact → Verification → Project Outcome**.
4. Mission / Operation objects are bounded sequencing and audit envelopes. Their `completion_criteria`, lifecycle status, report, or CEO interpretation cannot close or fail a Project.
5. Models propose. Deterministic application code commits authority-bearing state transitions.

## 2. Completion and evidence

1. Work is accepted only with durable Artifact evidence and a passing VerificationRecord.
2. Project completion is evaluated against the immutable Founder Project Contract across accepted Project evidence.
3. A Mission being completed is evidence availability, not Project completion.
4. A Project enters Result Ready only after Project-level evaluation proves all Founder criteria.
5. Result Ready itself must produce a durable Project Result Artifact and Project Contract Outcome verification.
6. Semantic model review may help bind non-identical evidence to a criterion, but cannot modify the criterion or manufacture missing evidence.

## 3. Failure boundaries

1. **Execution failure ≠ Work failure.** A failed provider/tool attempt may be retried or recovered inside Work policy.
2. **Work failure ≠ Mission failure** until bounded Work recovery is exhausted.
3. **Mission failure ≠ Project failure.** It is evidence for Project-level continuation/replanning.
4. Internal runtime/provider faults must use bounded recovery. They may not be surfaced as fake Founder decisions.
5. Ambiguous external effects require reconciliation before replay.
6. Budget or deadline exhaustion blocks further authority; it does not let an AI silently expand Project authority.

## 4. Budget authority

1. Project budget is the Founder-approved hard execution envelope.
2. Mission and Work budgets are bounded internal allocations inside that Project envelope, not independent Founder authority.
3. If the Founder states a numeric hard cap, that exact cap is the base Project envelope and may not be expanded internally. Only a later explicit Founder budget decision may append a budget amendment.
4. If the Founder does not state a numeric cap, approval must still show one deterministic system-priced Project envelope before execution.
5. The default system-priced envelope may reserve only bounded continuation/recovery headroom. v0.20 reserves the first Mission plus one additional bounded move and one continuation-planning reserve.
6. Any spend beyond remaining Project authority requires a real Founder budget authorization event.
7. A Founder budget authorization appends a hash-validated Project Contract Amendment and updates the effective authority ledger; it never rewrites the base Contract. Direct mutation of `Project.real_budget_limit` without a matching valid amendment is invalid authority.
8. Result Ready / terminal Projects cannot receive new budget amendments.
9. Provider planning cost incurred before Project approval is Company cost, not retroactive consumption of an execution envelope that did not yet exist.

## 5. Autonomous continuation

1. The CEO may create the next smallest useful Mission only inside an existing Founder Project Contract.
2. Delegated Missions must be stamped `PROJECT_DELEGATED_CEO` and must not create a fake pending Founder approval.
3. Delegated continuation cannot alter Project objective, success criteria, constraints, deadline, or budget.
4. Continuation planning is deduplicated against durable Project evidence fingerprints.
5. Repeated planning/review faults are bounded. Exhaustion becomes explicit system recovery or Founder authority need, never an infinite scheduler loop.

## 6. Restart and durability

1. Browser state and in-memory thread state are never business truth.
2. After process restart, the runtime resumes from durable Work / Execution / external-effect checkpoints.
3. Terminal Missions remain terminal history on restart. They must not be reset to RUNNING merely to continue a Project.
4. Normal application boot may perform schema-safety upgrades, but may not replay historical business migrations or legacy cutovers.
5. Historical imports and v0.20 cutover are explicit one-time migration operations with runtime threads disabled.

## 7. External effects and replay

1. A provider/tool call must cross the durable ExternalEffectAttempt boundary.
2. Safe replay requires deterministic evidence that dispatch did not happen, or a provider/idempotency mechanism that proves replay safety.
3. A restart after ambiguous dispatch must open reconciliation rather than duplicate the effect.
4. Retry policy is scoped to the Work / effect, not inferred from a generic Operation status.

## 8. Founder surface truth

1. Founder UI is a projection of Company Truth, never a second state machine.
2. UI may not show fake activity, fake Employees working, fake meetings, fake approvals, or synthetic completion.
3. An ACTIVE Project with a failed bounded Mission must be presented as recovering/continuing, not globally failed.
4. Founder approval must expose the Project authority being approved, including the total Project budget envelope and the first bounded Mission allocation.
5. Deep management surfaces may change radically, but they must preserve these truth semantics.

## 9. Legacy boundary

1. Legacy runtime code may remain for explicit migration and narrowly isolated compatibility behavior.
2. Legacy Project closure/failure functions may not be reachable from the v0.20 normal Project governing path.
3. Pre-v0.20 Project statuses created by Mission-level closure/failure are historical claims and must be re-evaluated against the Founder Project Contract during migration.
4. Compatibility fields may be projected for older UI/code, but may not regain governing authority.

## 10. Release acceptance

A release is not accepted because tests are green. v0.20 requires all three gates:

- **Structural gate:** governing imports, state writers, boot/migration boundaries, and authority stamps match this Constitution.
- **Executable engineering gate:** focused invariant tests, migration tests, compile checks, and regression diagnostics show no new blocking defect.
- **Founder Product gate:** a real Windows Project with the configured live provider/Codex runs end-to-end from Founder Project approval through Work, Artifact/Verification, autonomous continuation or bounded recovery, and Result Ready, with truthful cost/contribution/history visible.

Any contradiction between implementation and this Constitution is a release-blocking defect unless the Founder explicitly changes the Constitution.
