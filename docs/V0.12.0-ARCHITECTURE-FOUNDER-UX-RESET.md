# Eason One V0.12.0 — Architecture / Founder UX Reset

## Product contract

V0.12 removes the assumption that every Founder request should become a large Operation or Meeting. The CEO is the Founder-facing interface, while deterministic code owns routing, authority, state, budget, checkpoints, and termination.

The command path is:

`Founder Command → Deterministic Route → Authority Gate → Durable Operation → Worker/Tool → Verification → Result`

## Five routes

1. `DIRECT_RESPONSE` — persisted information or judgment is enough; no Operation is created.
2. `DETERMINISTIC_ACTION` — pause, resume, cancel, and cost/status actions run without a model.
3. `SINGLE_WORKER` — one bounded specialist Task; this is the default execution route.
4. `SHORT_MEETING` — explicit cross-role conflict only; one round and at most two specialists by default.
5. `FULL_PROJECT` — multiple dependent Tasks, stages, or deliverables.

The LLM may propose content inside the selected route. It cannot enlarge the route, budget, retry count, or Meeting authority.

## Authoritative Operation state

`CREATED → ROUTED → WAITING_APPROVAL → QUEUED → RUNNING → WAITING_INPUT / WAITING_APPROVAL → VERIFYING → COMPLETED / FAILED / CANCELLED`

`operation.kernel_status` is authoritative. The old `operation.status` remains a compatibility projection for existing pages and tests. Every transition creates an append-only `operation_event` row.

The initial Founder gate is distinguished by `approved_at is NULL`. It remains `PLANNED` in the legacy UI; later gates project as `WAITING_FOR_FOUNDER`.

## Durable execution

The database, not the browser page or Python thread, owns execution truth:

- DB-backed `QUEUED` state
- worker lease and expiry
- persisted checkpoint JSON
- step idempotency keys
- stale-worker recovery after restart
- append-only authority events
- no replay of a completed logical step

Threads remain local execution helpers only.

## Cost authority

Every non-mock provider call must first create a `cost_reservation`. Runtime rejects the call before provider invocation when any hard rule would be violated:

- Operation hard cost cap
- stage cost cap
- single-call cost cap
- maximum provider calls
- maximum revisions
- maximum elapsed time
- reserved or ambiguous spend

Exact usage consumes the reservation. Unknown usage remains `AMBIGUOUS` and continues to reduce available authority until the Founder resolves it.

## Bounded Meeting lifecycle

A Meeting is an explicit escalation object created at approval, not a hidden post-Task side effect.

`PLANNED → WAITING_FOR_INPUTS → READY → ACTIVE → SYNTHESIZING → COMPLETED / FAILED / CANCELLED`

Meeting state is saved in `meeting.kernel_status`; each transition creates a `meeting_event`. Round, speaker, token, cost, and message limits remain hard limits. Meeting is absent from the primary navigation and is entered contextually from a Mission.

## Founder UX

The Mission first screen now shows:

- authoritative state and current stage
- chosen route and route reason
- estimated cost, hard cap, actual spend, reserved spend, available authority
- provider call and revision counters
- checkpoint/worker state
- authoritative event count and event log
- explicit Founder gate actions
- existing Artifacts and verification evidence

The primary navigation hides People and Meetings during the reset. Their routes remain available for historical inspection and contextual links.

## Migration

`scripts/migrate_v0120.py` is additive and idempotent. It:

- backs up the SQLite database unless `--no-backup` is supplied
- adds Operation/Meeting kernel columns
- creates event and reservation tables
- imports legacy lifecycle states
- restores historical provider call counts and cost stages
- reconciles terminal CEO-created Projects
- preserves all existing records

Historical Meetings without a trustworthy Operation link remain unlinked. V0.12 does not fabricate provenance. All newly approved Meetings are linked at creation.

## Deliberate non-goals

V0.12 does not add LangGraph, Temporal, another Agent framework, embeddings, autonomous hiring, contribution scoring, salary/promotion logic, or richer Meeting simulation. Those remain gated behind successful real-project dogfooding.
